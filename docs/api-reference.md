# Motor Portal — API Reference

Generated by reading the real controllers in
`MotorPortalAPI/MotorPortal.API/Controllers/*.cs` and the real DTOs in
`MotorPortalAPI/MotorPortal.Application/DTOs/*.cs`. This reflects what
actually shipped, not the original LLD's planned endpoint list — a few
things differ from that plan (see notes inline) and this document is the
one to trust.

Base URL (local dev): `http://localhost:5795/api` (see
`MotorPortal.API/Properties/launchSettings.json`).

All request/response bodies are JSON unless noted (file upload/download
endpoints use `multipart/form-data` or a binary stream). All C# property
names below are shown as they serialize over the wire — camelCase, per
ASP.NET Core's default JSON naming policy.

## Auth

Every controller requires a valid JWT bearer token (`Authorization: Bearer
<token>`) **except** `AuthController` and `HealthController`, which are
explicitly `[AllowAnonymous]`.

### AuthController — `api/auth`

| Method | Path | Auth | Request | Response | Purpose |
|---|---|---|---|---|---|
| POST | `/api/auth/login` | none | Body `LoginRequestDto { username, password }` (both required) | `200 LoginResponseDto { token, username, role, expiresAt }`; `401 { message }` on bad credentials | Validates against `user_master` (bcrypt-checked `password_hash`, requires `status = 'A'`) and issues a signed JWT (`user_id`/`username`/`role` claims) |
| POST | `/api/auth/logout` | none | — | `200 { message: "Logged out." }` | Stateless — just tells the client to discard its token |

### HealthController — `api/health`

| Method | Path | Auth | Request | Response | Purpose |
|---|---|---|---|---|---|
| GET | `/api/health` | none | — | `200 { status: "healthy", database: "connected", timestamp }`; `503 { status: "unhealthy", database: "disconnected", timestamp }` | Real DB round trip (`SELECT 1`) — not a static ping |

### SecureTestController — `api/secure-ping`

Not part of the business API surface — a trivial `[Authorize]`-protected
endpoint kept from the early scaffolding phase to prove JWT auth works.

| Method | Path | Auth | Request | Response | Purpose |
|---|---|---|---|---|---|
| GET | `/api/secure-ping` | JWT | — | `200 { message: "pong", user }` | Proves `[Authorize]` rejects unauthenticated calls (401) and accepts valid ones |

## Batches — `api/batches`

All require JWT.

| Method | Path | Request | Response | Purpose |
|---|---|---|---|---|
| GET | `/api/batches?fromDate=&toDate=` | Query `fromDate`, `toDate` (optional `DateOnly`) | `200 [ BatchSummaryDto ]` — one row per batch: `{ batchId, totalRecords, validRecords, invalidRecords, pendingProcessing, paymentPending, paymentProcessed, status, createdOn }` | Per-batch summary counters, optionally filtered by `created_on` date range |
| GET | `/api/batches/summary-counters?fromDate=&toDate=` | Query `fromDate`, `toDate` (optional) | `200 BatchSummaryCountersDto { totalRecords, validRecords, invalidRecords, pendingProcessing, paymentPending, paymentProcessed }` | The same counters summed across every matching batch, for dashboard cards |
| POST | `/api/batches/upload` | `multipart/form-data`: `productId` (int), `functionId` (int), `file` (`.xlsx`, ≤ 20 MB via `[RequestSizeLimit]`) — bound as one `BatchUploadRequest` wrapper so Swashbuckle can render the operation | `200 BatchUploadResultDto { batchId, totalRecords }`; `400 { message: "The uploaded file is invalid.", errors: [ ExcelRowErrorDto { row, reason } ] }` if structurally invalid | Parses the Excel (ClosedXML), creates `batch_master` (`UPLOADED`) + one `batch_detail` (`PENDING`) row per record; inserts nothing on a structural failure |
| GET | `/api/batches/{id}/sample-template` | Route `id` (unused by the implementation — always returns the same static template) | `200` — `.xlsx` file stream | Downloadable sample template with the required header row + example rows |
| POST | `/api/batches/{id}/process` | Route `id` | `200 BatchProcessSummaryDto { batchId, validCount, invalidCount, premiumCalculated, proposalsCreated, status }` | Runs `sp_process_batch_validation`, then premium → GST → proposal generation for all valid records, advancing status through `PREMIUM_CALCULATED → GST_CALCULATED → PROPOSAL_CREATED` |
| GET | `/api/batches/{id}/status` | Route `id` | `200 BatchStatusDto { batchId, fileName, status, totalRecords, validRecords, invalidRecords, createdOn, premiumCalculatedCount, gstCalculatedCount, proposalsCreatedCount, paymentsProcessedCount, policiesCreatedCount }` | Current batch row plus live per-stage counts — polled every 2.5s by the batch-processing UI |
| GET | `/api/batches/{id}/invalid-records` | Route `id` | `200 [ InvalidRecordDto { transitDate, invoiceNo, engineNo, chassisNo, errorRemarks } ]` | Lists `invalid_records` for the batch |
| DELETE | `/api/batches/{id}/invalid-records` | Route `id` | `204 No Content` | Clears `invalid_records` for the batch and zeroes `batch_master.invalid_records` |
| POST | `/api/batches/{id}/payments` | Route `id` | `200 PaymentBatchResultDto { batchId, results: [ PaymentCaseResultDto { proposalId, success, message } ], succeededCount, failedCount, policiesCreated, batchStatus }` | Tags payment (`sp_tag_payment`) for every proposal in the batch without a processed payment yet; insufficient-CD-balance and other DB errors are caught **per case** and reported, never a batch-wide 500; creates `policy_master` rows for newly-successful payments and advances status through `PAYMENT_PENDING → PAYMENT_PROCESSED → POLICY_CREATED` as applicable |
| POST | `/api/batches/{id}/bulk-print` | Route `id` | `200 BulkPrintResultDto { batchId, status, certificates: [ BulkPrintItemDto { policyId, policyNo, certPath } ] }` | Generates a certificate PDF for every policy in the batch and advances status to `PRINTED` |

## Policies — `api/policies`

All require JWT.

| Method | Path | Request | Response | Purpose |
|---|---|---|---|---|
| GET | `/api/policies/search?engineNo=&chassisNo=&tcNo=&policyNo=` | Query, all optional strings but **at least one required** (400 otherwise) | `200 [ PolicySearchResultDto { policyId, policyNo, make, model, engineNo, chassisNo, premium, status, issuedOn } ]` | Searches `policy_master`, joined through `proposal_master → batch_detail` for `tcNo` (which only exists on `batch_detail`). Note `PolicySearchResultDto` has **no master-policy field** — a known gap the WEB app works around by preferring caller-passed router state |
| POST | `/api/policies/cancel-upload` | `multipart/form-data`: `file` (`.xlsx`, single `POLICY_NO` column, ≤ 20 MB) — plain `IFormFile` parameter (no wrapper needed since it's a single file field) | `200 PolicyCancelUploadResultDto { cancelled: [string], rejected: [ PolicyCancelRejectionDto { policyNo, reason } ] }` | Cancels each existing, not-already-cancelled policy (`status → CANCELLED`, one `audit_log` row per success); reports the rest as rejected (`"Policy not found"` / `"Policy already cancelled"`) — always `200`, never all-or-nothing |
| POST | `/api/policies/{id}/certificate` | Route `id` | `200 { policyId, certPath: "/certificates/{id}.pdf", generatedFile }` | (Re)generates the policy's certificate PDF (QuestPDF) under `wwwroot/certificates/{id}.pdf` and upserts `policy_certificate` |
| GET | `/api/policies/{id}/certificate` | Route `id` | `200` — PDF byte stream, `Content-Type: application/pdf`, filename `policy-{id}-certificate.pdf` | Streams the certificate PDF, generating it on demand if missing |

## MasterPolicies — `api/master-policies`

All require JWT.

| Method | Path | Request | Response | Purpose |
|---|---|---|---|---|
| GET | `/api/master-policies` | — | `200 [ MasterPolicyDto { masterPolicyId, masterPolicyNo, customerNo, cdbgNo, productId } ]` | Dropdown list of master policies (dashboard's CD Balance drawer) |
| GET | `/api/master-policies/{id}/cd-balance` | Route `id` | `200 CdBalanceDto { masterPolicyId, masterPolicyNo, cdBalance }` | Live read of `master_policy.cd_balance` for one master policy |

## Reports — `api/reports`

Requires JWT.

| Method | Path | Request | Response | Purpose |
|---|---|---|---|---|
| POST | `/api/reports/policy-issue` | Body `PolicyIssueReportRequestDto { fromDate, toDate }` (`DateOnly`) | `200` — `.xlsx` file stream (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`) | Queries `"SGInsurance".vw_policy_issue_report` filtered by issued date, writes a `report_log` row (`report_type = POLICY_ISSUE`), streams a generated workbook with columns matching `PolicyIssueReportRowDto` (`batchId, policyNumber, proposalNumber, masterPolicy, product, make, model, engineNumber, chassisNumber, premium, paymentStatus, issuedDate, user`). Always returns `200` with a valid workbook even for an empty date range — there is no "no data" error case |

## Error shape

The global exception middleware (`ExceptionHandlingMiddleware`) returns a
consistent JSON body for any unhandled exception:

```json
{ "statusCode": 500, "message": "...", "traceId": "..." }
```

`BusinessRuleException` and `ArgumentException` map to `400`; everything
else maps to `500`. Individual controllers also return their own explicit
`400`/`401`/`404`-style bodies for expected validation failures (shown per
endpoint above) — these take precedence over the generic middleware shape.

## Deviations from the original LLD's planned endpoint list

- The batch upload endpoint binds via a single `[FromForm] BatchUploadRequest`
  wrapper class rather than separate scalar + file parameters — required for
  Swashbuckle to render the multipart operation at all; the wire format
  (`productId`, `functionId`, `file` form fields) is unchanged.
- `GET /api/batches/{id}/sample-template` ignores `id` and always returns
  the same static template — there was never a need for per-batch templates
  in the shipped design.
- `BatchSummaryDto` (from `GET /api/batches`) names its counter
  `pendingProcessing`; `BatchSummaryCountersDto` (from
  `GET /api/batches/summary-counters`) also uses `pendingProcessing` (both
  endpoints were aligned to the same field name — see `changelog.md`'s
  integration-pass entry, which fixed an earlier inconsistency where the
  counters endpoint used `pendingBatchProcessing`).
- `PolicySearchResultDto` has no master-policy number field — a real,
  confirmed gap the frontend documents and works around rather than papering
  over.
